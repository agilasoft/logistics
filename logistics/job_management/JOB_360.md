# Job Management 360 Analytics

This module exposes a unified analytics layer keyed off `Job Number` that joins
operational data from every supported job DocType with financial data (GL, AR,
AP), recognition state (WIP, Accrual), and document alerts.

The layer is implemented in [job_360.py](job_360.py) and consumed by:

- 14 **Script Reports** under [report/](report/) prefixed `job_*`. The two
  headline surfaces are:
  - [`Job Explorer 360`](report/job_explorer_360/) — per-Job drill-down
    (replaces the retired `/app/job-360-explorer` Page).
  - [`Job Management 360`](report/job_management_360/) — monthly executive
    summary (replaces the retired `Job Management 360` Dashboard).
- 10 **Number Cards** under [number_card/](number_card/), pinned on the
  Job Management workspace next to the two report shortcuts.
- 10 **Dashboard Charts** under [dashboard_chart/](dashboard_chart/) —
  still available as standalone charts; the report-embedded charts are
  rendered by the report `execute()` directly.
- 6 **Notification** rules under [notification/](notification/) and matching
  scheduler hooks in `hooks.py`

## Data join key

`Job Number` is the registry; every operational job creates / links to one. The
`job_number` accounting dimension flows onto:

- `Sales Invoice.job_number` (header) → `GL Entry.job_number`
- `Purchase Invoice.job_number` (header) → `GL Entry.job_number`
- Recognition Journal Entries created by [recognition_engine.py](recognition_engine.py)

Profitability is computed two ways:

- **Detailed (per-job)** by
  [`logistics.job_management.api.get_job_profitability_from_gl`](api.py) which
  consults the per-job recognition policy. Used by the Job Number form's
  Profitability dialog and the per-job drill-down on the explorer page.
- **Bulk (one SQL grouped by job_number)** by ``_bulk_gl_rollup`` in
  [job_360.py](job_360.py). Used by every list-style consumer (the explorer
  page, the dashboards, every script report). It classifies GL lines via
  ``Account.job_profit_account_type`` plus ``root_type`` so it scales to
  thousands of jobs without the per-job N+1 cost. The two paths agree to
  within rounding for accounts that are tagged correctly; the per-job path
  is the source of truth when the policy account differs from the
  classification.

## Performance contract

Both headline Script Reports (`Job Explorer 360` and `Job Management 360`)
call `get_job_360_rows` exactly once per run, which internally runs
`_bulk_gl_rollup` once and `get_jobs_ar_summary` / `get_jobs_ap_summary`
once. Chart and summary tiles are aggregated server-side from that one
row set, so each Run is a single backend round-trip. With ~1.5k jobs each
report completes in ~1 s; with the default 90-day scope it is sub-second.

The legacy single-shot endpoint `get_job_360_payload` (originally for the
retired `/app/job-360-explorer` Page) is kept for any external integrations
that consume the same KPI + chart + paginated rows shape.

Document alerts use `_bulk_document_alerts`, a single SQL query against
`tabJob Document` grouped by parent, instead of loading each parent
operational doc — used by both the alerts report and the explorer page when
alerts are requested.

## Adding a new operational doctype

To plug a new operational doctype into the Job 360 layer, add a row to
`JOB_TYPE_FIELD_MAP` in [job_360.py](job_360.py):

```python
JOB_TYPE_FIELD_MAP["My New Job Type"] = {
    "customer": "customer",         # source field on the doc
    "origin": "origin_location",
    "destination": "destination_location",
    "status": "job_status",
    "ops_status": "operational_status",
    "etd": "scheduled_start",
    "eta": "scheduled_end",
    "mode": "transport_mode",
    "vehicle_or_carrier": "carrier",
    "estimated_revenue": "estimated_revenue",
    "estimated_costs": "estimated_costs",
    "wip_amount": "wip_amount",
    "accrual_amount": "accrual_amount",
    "recognized_revenue": "recognized_revenue",
    "recognized_costs": "recognized_costs",
    "billing_status": "billing_status",
    "sla_status": None,
}
```

Any field that doesn't exist on the source doctype is ignored. The layer is
deliberately defensive: missing fields, missing doctypes, and non-installed
modules silently skip without breaking the report.

## Notifications

Six Notification doctype records under [notification/](notification/) plus
six daily scheduler hooks in [../hooks.py](../hooks.py) drive the alert
behaviour:

| Rule                              | Schedule           | Helper                                  |
| --------------------------------- | ------------------ | --------------------------------------- |
| Job Margin Below Threshold        | Daily              | `notify_jobs_below_margin`              |
| Job Negative Margin               | Daily              | `notify_jobs_negative_margin`           |
| Job WIP Stale                     | Daily (>60 days)   | `notify_stale_wip`                      |
| Job Accrual Stale                 | Daily (>60 days)   | `notify_stale_accrual`                  |
| Job AR Overdue                    | Daily (>30 days)   | `notify_overdue_ar`                     |
| Job Closed With Open Balances     | On save / scheduler | `notify_closed_jobs_with_balances`      |

The helpers return the candidate jobs and create `Notification Log` records
addressed to each job's owner.

## Filter contract

All reports / cards / page accept the same filter dict:

```python
{
    "company": str,
    "branch": str,
    "cost_center": str,
    "profit_center": str,
    "job_type": str,
    "from_date": "YYYY-MM-DD",
    "to_date": "YYYY-MM-DD",
    # extras (some reports only)
    "margin_threshold": float,   # Margin Watchlist
    "stale_days": int,           # Recognition Aging
}
```

`from_date` / `to_date` apply to `Job Number.creation` for scoping; the GL
roll-up uses them as the GL Entry posting-date window in
`get_job_profitability_from_gl`.

## Public Python API

```python
from logistics.job_management.job_360 import (
    get_job_360_rows,
    get_job_360_payload,        # single-shot endpoint for the explorer page
    get_job_360_table,          # paginated rows only
    _bulk_gl_rollup,            # SUM(GL Entry) GROUP BY job_number
    _bulk_document_alerts,      # SUM(Job Document) GROUP BY parent
    get_jobs_ar,
    get_jobs_ap,
    get_recognition_aging,
    get_job_status_pipeline,
    get_alerts_summary,
    get_dashboard_kpis,
)
```

All are pure read-only and safe to call from server scripts, custom
reports, or external integrations.
